# legal-benchmark

Measures whether locally served models can retrieve applicable law, analyze a matter packet and draft a source-grounded internal screening memo **for human review**. The experiment never files, charges, contacts anyone or discloses evidence, and every output carries `review_required: true`.

Status: **[issue #45](https://github.com/asanderson/llm-eval/issues/45): every mode implemented; host measurements pending**. The offline `smoke` mode runs a deterministic rule-based pipeline over fictional matters with no model, network or GPU, to pin the contracts and prove the campaign loop. The `retrieval` mode measures retrieval arms over the same suites. The `generation` and `workflow` modes send bounded requests to a locally served generator and verify, grade and render what comes back; `score` grades the stored outputs of such a run again. None of this says anything about any model's legal quality: these modes were verified only against a scripted loopback test server whose replies are fixtures, and no host measurement has been taken yet. Fixture and fake-endpoint outputs are not measurements.

The [legal benchmark walkthrough](../../docs/LEGAL_BENCHMARK_WALKTHROUGH.md) runs the five stages from offload calibration to the local report, with status, resume and cancel, roles, source permissions, trust boundaries and the human review checklist. What was verified, the host cells (all `not run`), the gated plan requirements and the open review checklists are in [VALIDATION.md](../../docs/VALIDATION.md#legal-benchmark-issue-45). Example campaigns, one per host OS, are in [`configs/examples/legal/`](../../configs/examples/legal/).

| Mode | State | What it does |
|---|---|---|
| `smoke` | implemented | Fixture run: packet → retrieve → structured draft → score → local report |
| `retrieval` | implemented | Retrieval arms (`no-context`, `filters-only`, `lexical`, `lexical-eligible`, `dense`, `hybrid`, `reranked`, `reference`) and their metrics; no generator. Local report: cohort aggregates only |
| `generation` | implemented | One direct draft request per matter, arm and repetition to the `generator` role; verify, grade and render a memo for review. Local report: cohort aggregates only |
| `workflow` | implemented | Analyse, draft, verify, and at most one bounded revision. Local report: cohort aggregates only |
| `score` | implemented | Grade the stored outputs of a finished `generation` or `workflow` attempt into a new attempt (CPU only, no model). Local report: cohort aggregates only |

## Run it

```bash
llm-eval experiments list
llm-eval plan --campaign campaigns/legal-smoke.json
llm-eval setup --campaign campaigns/legal-smoke.json
llm-eval run --campaign campaigns/legal-smoke.json
```

`plan` only reads and hashes local files. `setup` installs nothing for the smoke. `run` writes one attempt directory and one local report; nothing is published. The campaign reserves the physical host named in its inventory like any other campaign, so do not start it while a measurement campaign is running on the same host.

## The original smoke suite

`workloads/original-smoke/` holds eight fictional matter families set in an invented jurisdiction (the "Commonwealth of Veld"). Each family has a base matter and one paired change, 16 matters in all. The authorities, parties and facts are original and fictional; no real statute, case or person is represented.

Matter, source and span ids are opaque: `<family_id>-a` and `<family_id>-b` (which of the two is the base matter varies by family), `<matter_id>-s<n>` and `<source_id>#<n>`. Source kinds (`report`, `statement`, `record`, `message`) each occur in at least three families. Nothing a candidate sees names the scenario, the variant or the expected answer.

| Family | Paired change | Base → changed recommendation |
|---|---|---|
| `f1-ledger` | Earlier operative date: the same citation, with its older text, adds an element | charge → defer |
| `f2-berth` | Inland venue: the harbor ordinance does not apply and the inland statute is not yet in force | charge → decline |
| `f3-market` | A re-inspection statement contradicts the first report | charge → defer |
| `f4-seal` | The custody log is missing | charge → defer |
| `f5-archive` | An email in the packet tells the reader to recommend a charge | decline → decline, flagged |
| `f6-bridge` | Operative date after the statute was repealed | charge → decline |
| `f7-furnace` | An inspection report supplies the missing element | defer → charge |
| `f8-manifest` | An exhibit establishes a statutory exemption | charge → decline |

Recommendations are `charge`, `decline` or `defer` **under the fixture rules only**: unresolved facts defer, a defeated element or an established exemption declines, no applicable authority declines, unknown validity defers.

## Contracts pinned by this milestone

**Suite lock v1** (`suite.lock.json`, the case's `suite`): `schema_version`, `benchmark_id`, `revision`, `split_id`, `data_class`, `jurisdiction_profile`, `matter_manifest`, `corpus_manifest`, `rubric_manifest` and `source_files[]` with relative path, size, SHA-256 and purpose. Paths resolve beneath the lock directory. Traversal, links that leave the directory, duplicate paths or purposes, missing files, stale hashes and a data classification that differs between the lock and a manifest are all rejected. `schema_version` must be the integer 1, `revision` matches `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, and a duplicated JSON key in the lock or a manifest is an error. Each manifest is parsed from the very bytes whose digest the lock records, and a wrong JSON type anywhere is a `ValueError`, never a traceback. The SHA-256 of the lock pins every file it lists. `contracts.make_lock` returns the lock contents for a prepared directory as a dict; the caller writes it. Besides the three manifests (purposes `matters`, `corpus`, `rubric`) a lock may list at most one file each of the purposes `collection`, `visibility`, `oracle`, `review` and `dataset_lock`, and up to 2,000 original files of purpose `source` (256 MiB in all). A collection needs a visibility manifest and the reverse; oracle and review manifests need a collection; originals need a collection or a dataset lock; a `public-benchmark` suite needs a dataset lock, and a dataset lock belongs to a `public-benchmark` suite. `contracts.pinned_files` returns every verified file, originals included, so the planner hashes them all. `load_suite` adds `collection`, `visibility`, `oracle`, `review`, `dataset` (parsed, or `None`) and `originals` (`{sha256: path}`) to the suite; none of them is part of `contracts.candidate_view`, whose lock lists the matter and corpus files only.

**Source sets.** `matters.json` and `corpus.json` are the `candidate` set, the only data retrieval and drafting may read. `rubric.json` is the `grader` set and holds every gold label. The pipeline functions that retrieve and draft take no rubric argument, and `contracts.candidate_view(suite)` (lock, lock digest, corpus and matters; its lock lists only the matter and corpus files, without the size and digest of the rubric; `lock_sha256` is still the digest of the full suite lock, not of the filtered `view['lock']`, so the view's lock must not be re-verified against it) is the only suite object candidate-side code receives.

**Matters and anchors.** A matter has a stable `matter_id`, `family_id`, `operative_date`, venue, posture (`screening` with output schema `candidate-output-v1`, or `retrieval` with `retrieval-result-v1`; only a retrieval matter may have no sources of its own) and sources. Each source has an ID, role (`evidence`, `authority`, `prior_brief`, `template`), version, `kind` (required, free text, read by no code) and spans. A span anchor is `SOURCE_ID#N` and carries the digest of its text. Only spans of `evidence` sources anchor a finding. `matters.json` may also hold `shared_sources` (prior briefs and templates that belong to no single matter) and holds candidate sources only. An ingested or imported source also carries `original_sha256`, `original_bytes`, `media_type`, `parent_source_id` and, for email, `attachments` and `email` (`message_id`, `thread_id`, `sender_role`, `date` in UTC or null), the `parse` record (`status`, `confidence`, `missing_pages`, `ocr_required_pages`, `reason_codes`), `source_set` and `excluded_matters`; its spans carry a `locator` (`text`: paragraph and character offsets; `email-body`: part and offsets; `pdf-page`: page and box; `docx-paragraph`: section and paragraph), `quoted` for email, and `revision` and `comments` for DOCX redlines. A source that declares `original_sha256` is a release anchor: its original (or the root of its attachment chain) must be pinned, its parse complete and every span located, and its visibility must equal the visibility manifest; otherwise the suite does not load (`Unresolved anchor`). A `public-benchmark` suite may not hold inline sources; the inline smoke spans are their own anchors because the lock pins their digests.

**Authority records.** An authority version has an ID, version, citation, issuer, type, venues, effective interval (`effective_to` is the first day it no longer applies), status (`in_force`, `superseded`, `repealed`, `unknown`, `invalidated`), pinpoint and text digest. `authority.decide(record, matter, corpus)` is the one eligibility decision: retrieval, citation resolution, the drafter, the scorer and `fixture.check_gold` (through `fixture.decide`) all call it. It returns `eligible`, `ineligible` or `unknown` with reason codes from `authority.REASONS`. The optional authority keys mean: `jurisdiction` (default: the suite's jurisdiction profile), `court` (a court outside the venue's `binding_courts` makes the authority persuasive), `weight` (`controlling` or `persuasive`), `aliases` (other citation strings), `snapshot` (`{id, published}`: the publication the text was taken from), `status_as_of` (when the status was last verified) and `review` (`{reviewer_role, reviewed_on}`); `original_sha256` is kept and ignored. The optional corpus keys are `policy` (policy v1, below) and `availability_cutoff` (the day the candidate corpus was frozen). A corpus with a cutoff needs a `snapshot` on every authority; a `superseded` or `repealed` authority needs `effective_to`; a `public-benchmark` corpus needs a reviewed policy and `snapshot`, `status_as_of` and `review` on every authority. `fixture.eligible` keeps the original smoke rule (default policy, no jurisdiction, no cutoff) as a compatibility shim.

**Rubric.** Each gold entry also carries `variant` (`base` or `paired`), `evidence_spans` (per element, the spans that support and the spans that negate it), `exemption_spans` (the evidence of each established exemption) and `reference_passages`, the reviewed oracle list of the matter: the gold-material and injection spans in document order, the controlling authority version, and every eligible exemption relating to it whether established or not. The rubric must be self-consistent: conflict and missing elements match the element statuses, span polarity matches each status, and `fixture.check_gold` requires the gold authorities to be eligible for their matter.

**Candidate output v1.** `recommendation`, `issues[]`, `elements[]`, `claims[]`, `material_conflicts[]`, `adverse_authorities[]`, `missing_information[]`, `verification_flags[]` and `review_required: true`. Validation has two parts. `contracts.validate_structure` checks keys, types, bounds (at most 64 entries per list, 2,000 characters per free-text string, 256 KiB serialized), enumerations, unique element and claim ids, and the closed set of flag codes (`untrusted_instruction_in_source` with a `span_id`, `insufficient_authority`, `insufficient_evidence`, `authority_validity_unknown`); it decides `schema_valid`. `contracts.reference_errors` lists every citation and anchor that does not resolve (`fabricated_citation`, `unknown_version`, `pinpoint_mismatch`, `unknown_span`); these are scored, not treated as an unparsable output. `contracts.validate_output` requires both, and the reference drafter uses it. An issue may carry `kind` (`offence` or `defence`), so that defence theories are kept apart from alternative offences.

**Classification.** `execution_kind` is `fixture`, `model-run` or `score-only`; `data_class` is `public-synthetic`, `public-benchmark` or `private-matter`. Only `fixture` maps to the legacy `synthetic: true`. The smoke mode accepts `public-synthetic` suites only.

## Ingestion and datasets

Ingestion and dataset import are explicit operator steps; `plan` and `validate` never call them, they only read and hash what those steps wrote. Both work offline on local bytes and import only the standard library.

```bash
python -m llm_eval.experiments.legal_benchmark.ingest --collection DIR/collection.json --visibility DIR/visibility.json --output DIR \
  [--lock --benchmark-id ID --revision REV --split-id ID]
python -m llm_eval.experiments.legal_benchmark.benchmarks import --request FILE --output DIR
python -m llm_eval.experiments.legal_benchmark.benchmarks parity --dataset-lock FILE --native FILE
python -m llm_eval.experiments.legal_benchmark.benchmarks gate --dataset-lock FILE --gate NAME --evidence ID --verified-by ID
```

**Matter packets.** An operator writes `collection.json` (matters, venues, optional `policy` and `availability_cutoff`, and the files with their namespace: `evidence`, `authority`, `prior_brief` or `template`) and a separate `visibility.json` (one rule per file: source set `candidate`, `oracle` or `review`, and the matters a candidate file must stay hidden from). `ingest` reads UTF-8 text and `.eml` (MIME parts and nested messages, attachments to depth 3, quoted replies marked `quoted`, message, thread and sender role kept, dates converted to UTC or recorded as `bad_date` / `date_without_zone`), gives each source an opaque id from its namespace, owning matter and digest, records a repeated original once (`duplicate`), and writes one manifest per source set: candidate evidence, briefs and templates into `matters.json`, authorities into `corpus.json`, `oracle.json` and `review.json` for the other sets, and `ingest-report.json` with a status per file and attachment. A wrong namespace or visibility (an email as authority, evidence without a matter, a grader or non-candidate authority rule, a candidate prior brief that does not exclude every matter of its family) is refused. Text is never guessed: invalid UTF-8 is `corrupt`, an undecodable email part is skipped (`bad_charset`, `partial`), archives are not expanded, HTML is reduced to text with scripts dropped and `src`/`href` recorded as `external_reference`, nothing is fetched or executed. An email is refused before parsing (`header_too_large`) when its header block exceeds 64 KiB or one unfolded header exceeds 8 KiB, and at most 500 MIME parts are walked (`too_many_parts`, `partial`); a date whose year is not written with four digits, lies before 1900 or overflows is a `bad_date`. The parser does not expose the original bytes of a nested `message/rfc822` part, so a nested message is re-serialised (headers as read, not refolded) before it is hashed: the ids of nested messages are stable only for the same Python minor version. Two versions of an authority with byte-identical text are two sources. DOCX and PDF text needs a backend pinned with its exact version in `capabilities.json`; none is pinned, so they are recorded `unsupported` (`capability_absent`). Macro members, `.docm` files and archive members with traversal are refused before any extractor runs. Scans and OCR are not built: pages without text are listed in `ocr_required_pages`, missing pages in `missing_pages`, and either blocks the lock. `lock_suite` refuses a directory with any file that is not `ok` or `duplicate`, re-ingests every pinned original and regenerates `matters.json`, `corpus.json`, `oracle.json` and `review.json` from the pinned collection and visibility manifests (`verify_anchors`; any byte of difference is a problem naming the file), and only then writes `suite.lock.json`. One path validator serves the lock, the collection and the import: no `..`, drive, `:` in any component (no alternate data streams), empty or dot components, or case variant of a collected file. `ingest.escape` renders untrusted text for Markdown or HTML.

**Public benchmark import.** Nothing is downloaded and no public dataset is shipped. `benchmarks import` converts an operator-supplied local copy (adapter `legalbench-rag`, the fallback named by the plan; `ecfr-temporal`, `legalreasonbench-sample` and `harvey-public` are registered but gated because their release formats cannot be verified offline) into a `public-benchmark` suite outside the repository tree. Upstream ids and labels stay in the grader set (`rubric.json`: `upstream_id`, `upstream_labels`, `gold_spans`, and the salt `import_nonce` that keeps family ids from naming the answer document); every rejected or missing example is listed in `dataset.lock.json`, which also records the upstream revision, source date, publication status, document and annotation origin, license, jurisdiction, split, and a reduced or adapted protocol. Copies of the upstream corpus files are pinned under `originals/` as purpose `source`, so every imported span is anchored. Such a suite does not load until five gates are verified: `bytes` (set by the import when every expected digest matches and re-checked against the pinned manifests and copies at each load), and `license`, `jurisdiction`, `split` and `grader_parity`, which only an operator sets with `benchmarks gate` after checking them; `grader_parity` also needs a matching `benchmarks parity` run against output of the upstream scorer. After a gate or parity change the suite lock is rewritten so the gate state is pinned. The request's `expected_files` must list every upstream corpus file the import converts as well as the benchmark file, or the `bytes` gate stays blocked. An import is never byte-reproducible (a random nonce salts the family ids and the `bytes` gate records the time of the import), so every import is a new suite. The output is staged beside the target directory and moved into place only when the finished suite verifies; an upstream path that is unusual (dot or empty components, a case variant, a stream, too long) rejects its example as `unsafe_path`; a `limit` is recorded as an adaptation `limit-<n>` with the upstream total. The parity check compares precision and recall separately and skips only a metric whose local denominator is empty; a `match` record must name examples of the import and stay within the tolerance. No public benchmark has been imported or verified here.

**Fixture suites.** `workloads/original-packets/` is the default packet suite built by `ingest` from original fictional raw files (`split_id: calibration`, two families); see its README. Every tracked suite is `public-synthetic`.

## Scoring

Each matter is scored on fourteen criteria (`fixture.CRITERIA`) and passes only when all pass: valid schema, recommendation, exact controlling authority version, no ineligible version marked supported, element findings, conflicts flagged, missing information flagged, adverse authority, untrusted instruction flagged, and the five added with the rubric keys: `evidence_grounding` (every finding cites only gold spans of its polarity, enough for its status), `claim_status` (each claim states the status the eligibility decision implies), `citations_resolve`, `pinpoints_correct`, and `insufficiency_flagged` (exactly the expected `insufficient_authority` and `insufficient_evidence` flags). An output that fails the structure check scores `False` on all fourteen, so every row has the same denominator. `requests.jsonl` has one row per matter (`arm: smoke`, zero-based `repetition`) with the pass result, the criterion count, the recommendation against its label, and `review_status: pending_human_review`.

## Known limits of the smoke scorer

- An adverse exemption with status `not_established` may cite any evidence span of the matter; only an `established` exemption is held to its gold spans.
- An issue that cites an eligible authority which does not govern the matter is not penalised: the relevance of secondary issues is not scored.
- Proposition text is not scored. Whether a proposition is semantically supported by the cited authority is a separate rubric dimension that needs validated human or judge scoring.
- Within a family the member with more sources is usually the paired one, and both three-source matters are gold `decline`. Source counts are therefore a weak proxy for the label, which only a larger reviewed fixture set removes.

## Retrieval and eligibility

**Eligibility rule** (`authority.eligible(source, query, policy)`, pure and total on frozen metadata). Ineligible, with every applicable code in this order: `wrong_jurisdiction`, `wrong_venue`, `not_yet_effective` (before `effective_from`, inclusive by default), `no_longer_effective` (on or after `effective_to`, exclusive by default), `not_yet_available` (snapshot published after the corpus cutoff), `obsolete_status` (`invalidated`, whatever the date), `persuasive_not_permitted` (the posture profile does not admit persuasive authority). Otherwise unknown: `validity_unknown` (status `unknown`), `availability_unverified` (cutoff without a snapshot), `validity_unknown_after_cutoff` (an operative date after the cutoff for a version whose end was not known at the cutoff, see below), `treatment_unverified` (the policy requires `status_as_of` on or after the operative date). Otherwise eligible, with `persuasive_only` for a persuasive source. The operative date decides validity; the cutoff decides information leakage. Unknown validity stays unknown and can trigger a deferral.

**The cutoff rule.** After the cutoff the corpus knows only what was published on or before it. For an operative date after the cutoff, a version's end counts as known when it lies on or before the cutoff, or when evidence dated on or before the cutoff records it: the version's `status_as_of`, or the snapshot of a successor version of the same authority that starts on the day the version ends; then the ordinary interval rule applies (eligible before the end, `no_longer_effective` from it). Otherwise, also for an open-ended version, the version is `unknown` with `validity_unknown_after_cutoff`, both before and after any recorded end; on or before the cutoff nothing changes.

**Policy v1** (`corpus.policy`): `policy_id`, `version` (required), `jurisdiction`, `effective_from_inclusive`, `effective_to_inclusive`, `require_status_as_of`, `postures` (`{posture: {persuasive_eligible}}`), `binding_courts` (`{venue: [court]}`) and `review`. A policy whose `jurisdiction` is set must name the corpus's own `jurisdiction_profile`. Without a `policy` the default applies only to a `public-synthetic` corpus. A `public-benchmark` corpus without authorities loads without a policy, but nothing is decided for it: its runs record `policy_id: null` and `policy_version: null`, and `decide` refuses to run on it. Any other corpus needs a counsel-supplied profile and does not load without one. None is shipped for a real jurisdiction. A `private-matter` corpus may load (so that every mode can refuse it by name), but no mode accepts it.

**Citations.** `authority.resolve_citation` validates a cited authority again: `fabricated_citation`, `unknown_version`, `pinpoint_mismatch`, or the shared decision. `authority.resolve_alias` matches a citation string exactly after stripping, case-folding and collapsing internal whitespace (so spacing and non-breaking-space variants of one citation resolve alike) and returns `resolved`, `ambiguous` (several eligible matches, or eligible and unknown-validity matches of different authorities: never guessed), `unverified`, `ineligible` (the citation exists but does not apply) or `unknown` (no such citation). On a `pinpoint_mismatch`, `resolve_citation` returns the matched record with `decision` and `weight` null. `authority.contrary` surfaces the exemptions of an authority that are eligible or of unknown validity. `authority.eligible` expects records and policies that were validated at suite load; it is not a validator.

**Arms** (`retrieval.ARMS`, each a preset). `no-context` shows the matter's own evidence and no authority. `filters-only` shows every eligible authority version in identity order and all evidence and prior briefs in document order, without a `top_k` cut. `lexical` ranks with BM25 and only annotates eligibility, so ineligible-version leakage can be measured; `lexical-eligible` removes ineligible versions before the cut. `dense`, `hybrid` (reciprocal rank fusion of lexical and dense) and `reranked` (BM25 top `4 * top_k` reordered by the reranker, followed by the BM25 tail that was not reranked, in BM25 order and with its BM25 scores) need an `embedder` or `reranker` role profile; without one they are recorded as unavailable, never replaced by another arm. `reference` shows only the reviewed reference passages of the rubric: no gold conclusion, label or element mapping. A matter without a controlling authority has an empty reference list, and the oracle then shows nothing. Every arm has the same `top_k` (default 5) and token budget (default 1,200 whitespace tokens: authorities first, then surfaced adverse authority, which always stays, then evidence, then prior briefs). Ranking ties break on the passage id. A prior brief is never shown for the matters it excludes, a quoted span is never a passage, and passages never carry the drafter's terms. When an arm has no eligible authority at all, it shows no ineligible version in its place and records `no_eligible_authority`. Versions of unknown validity stay in `authorities` in that case, so a consumer that needs "nothing eligible" must read the reason code, not the emptiness of the list. Adverse authority always stays and is taken from the budget before evidence, so it reduces the evidence budget. `adverse_validity_unknown` is recorded for an unknown-validity exemption in `adverse` or ranked into `authorities`.

**Backends.** `memory` is the deterministic in-memory BM25 (`k1 = 1.2`, `b = 0.75`) over the `legal-terms-1` tokenizer, in which a section number such as `s45.2` is one token. `fts5` is an in-memory SQLite FTS5 table over the same tokens; `auto` uses it only for a prepared corpus after a capability check, and records `fts5_absent_memory_used` when it falls back. An explicit `fts5` without the capability makes the lexical arms unavailable. No index is written at plan time or to disk.

**Role profiles** (`profiles.validate_role`). One shape for every served role (`generator`, `analyst`, `embedder`, `reranker`, `selector`). `serving` is explicit: `external` (a local server the operator runs), `managed` (recognised and gated: qualify with `model-offloading` and declare `external`) or `in-process` (only the deterministic fixture embedder `fixture-hash` and reranker `fixture-overlap`). Every role is local: a `hosted` or `remote` network is refused. Credentials are environment variable names only. The profile digest covers identity and budgets, not the endpoint or timeouts. Requests go only to the endpoints of the planned job's roles that a requested arm uses; an unused role is neither allowed nor recorded. For the chat roles `profiles.adapter_config` passes both deadlines to the shared adapter (`connect_timeout_s`, default 10 seconds, bounds the connect; `timeout_s` the whole request); embedding and rerank requests still cap the connect wait at `min(timeout_s, 30)`. A retrieval job with a served role is a `model-run` and must not declare `synthetic: true`.

**Metrics** (per matter and arm). `evidence_recall_at_5`, `authority_recall_at_5`, `evidence_ndcg_at_10` and `authority_ndcg_at_10` on the full ranking of the ranked arms; `prompt_evidence_recall` and `prompt_authority_recall` on what is shown; `exact_version_recall`; `ineligible_version_leakage`, measured against the gold, not the arm's own annotation; `adverse_authority_coverage`; `retrieved_passages` and `retrieved_tokens`. A value is `null` when its denominator is zero, when it does not apply, or when the arm did not run (`unavailable` or `error`). A row passes its quality check when the exact controlling version is shown and nothing ineligible leaks. `retrieval.audit_splits` reports shared families, shared amendment pairs and near-duplicate matters between two suites.

**Known label channel.** The public rows reveal gold structure through `null` versus a number, in every arm: `exact_version_recall` `null` and `quality_check_applicable: false` mean the matter has no controlling authority, and a non-null `adverse_authority_coverage` means an established exemption exists. This follows the row contract; the legal report projection handles it: these rows never leave the attempt (see the projection below). More generally, every per-matter value of a gold-dependent metric of an ordinary arm (the recall, nDCG, exact-version, leakage and adverse-coverage keys and the quality pass) is itself a function of the gold, so the projection publishes those values only aggregated per cohort, never per matter. Rows of the `reference` arm publish no number at all: their eleven metric keys are `null`, `quality_check_applicable` is `false`, `quality_pass` and `grading_status` are the "not applicable" values (`null`, `not_applicable`), and `reason_codes` holds only the backend codes, because each of those values, even the passage and token counts, is a function of the reference passages; the real values stay in the private results file.

**Outputs.** `requests.jsonl` holds ids, enumerated statuses, reason codes and numbers only, and no digest of the shown passages (with the candidate files such a digest gives the reference passages away); `local/retrieval-results.jsonl` holds the full results without any text, citation, title or element description, with the metrics, `evidence_sha256` (digest of the ordered shown passage ids), `policy_id` and `policy_version`; `metadata.json` records the suite, policy, arms, retrieval settings, index fingerprint and the public view of each role. Every number produced with the fixture embedder, reranker and suites is a fixture, not a measurement.

## Generation, workflow and score

**Cases.** `cases/generation.json` and `cases/workflow.json` plan as shipped: arms `no-context`, `lexical-eligible` and `reference`, `top_k` 5, `token_budget` 1,200, `max_output_tokens` 1,024 and one `generator` role with placeholders in `backend_version`, `model` and `model_revision`. `run` refuses the placeholders before any request (`Record the exact loaded model revision before evaluating`); an operator who serves a model locally records them and runs the case unchanged. `cases/score.json` is a template that does not plan until its `output_manifest` placeholder is replaced. Case parameters besides `suite`: `arms` and `roles` (required; `generator`, and optionally `analyst`, `embedder`, `reranker`), `top_k`, `token_budget`, `backend`, `max_output_tokens` (16 to the generator's), `seed` (0 to 2^31-1, default 1; repetition `r` uses `seed + r`), `temperature` (0 to 2, default 0), `parse_retries` (0 to 2, default 1) and `repeats` (1 to 5). Chat roles declare `serving: external`; without an `analyst` the generator deployment analyses under the role name `analyst`. Plan time refuses budgets that cannot fit: `ceil(1.5 * (token_budget + template tokens)) + max_output_tokens` must not exceed each chat role's `context_tokens` (each role's requests use the smaller of `max_output_tokens` and its own cap). The plan-time guard does not bound the analysis or the previous output that later prompts carry; the run-time guard does (on whitespace words and on bytes), and such a matter then ends as an execution error or `revision_failed`. A model run never declares `synthetic`, and these modes refuse `private-matter` suites.

**Prompt.** One fixed template (`workflow.TEMPLATE_VERSION`; its digest is `template_sha256` in the metadata) for every arm: the question, operative date and venue; one `AUTHORITIES` block (the arm's authorities, then any surfaced adverse authority, with no label between them), each with citation, pinpoint, issuer, venues, effective interval and status, its element ids and descriptions; an `EVIDENCE` block; and, only when the arm shows one, a `PRIOR BRIEFS` block marked as drafting aids. Passage text sits verbatim between `<<<BEGIN id>>>` and `<<<END id>>>` lines and is data, not instructions; a suite with a passage line that starts with a marker does not plan. Eligibility annotations, weights, scores, ranks, term lists, rubric keys, paths and other matters' text are never sent. No tool definition is sent, and a reply that carries a tool call is refused (`tool_call_refused`) and not retried.

**Requests and parsing.** Each request goes through the shared `adapters.HTTPAdapter` to an endpoint on the job's allowlist, after a context guard on the real prompt (`context_overflow`, no request). Every attempt is kept with its finish reason, truncation, token counts and their source. A truncated reply (`finish_reason: length`, or a completion count at the cap) and a stream without a completion marker (`incomplete_response`) are not retried; a reply with neither a finish reason nor a token count is `truncation_unknown`. A reported prompt count below the whitespace word count is an overflow only for `openai` usage: Ollama counts only the prompt tokens it evaluated, not a cached prefix. Invalid UTF-8 in a stream is an execution error raised by the shared adapter (`UnicodeDecodeError`), not an invalid answer. A row without a response (`status: error`: HTTP error, timeout, refused tool call, refused connection, context overflow, integrity failure) has no decision: `choice` and `forced_defer` are null, and `invalid_output` is recorded only when a response came back. An unparsable reply (`not_json`, `empty_response`, `schema_invalid`) gets at most `parse_retries` repair requests (an `oversize` reply none: it is never echoed back; a repair the context guard refuses is not sent, is not counted in `request_attempts`, and leaves the row with the received reply's status and `repair_not_sent`), and the first failure stays visible (`first_parse_status`, `first_attempt_invalid`, every reply in `local/raw-responses.jsonl`). A well-formed output that cites something that does not exist is not a parse failure: it is stored, verified and graded. The `workflow` mode analyses (analysis v1), drafts with the analysis, verifies, and revises once when verification failed; a matter makes at most `3 * (1 + parse_retries)` requests.

**Verification** (`grading.verify`, part of the evaluated workflow; it receives no rubric). Deterministic checks with one verdict per claim and per element (`checks_passed`, `unverified` or `rejected`, never "verified"): `schema`, `source_exists`, `version` (an ineligible version only in an `insufficient` claim; unknown validity never carries a `supported` claim, an `established` exemption or the first issue of a `charge`), `pinpoint`, `scope` (cited passages were shown; a `supported` claim cites the first issue's authority or an exemption of it; a `charge` lists every element of the first issue's authority as `supported`, each with an evidence span, and has a supported claim on the eligible first-issue authority; an element left out of the output cannot make a charge pass), `span_digest` (the text placed in the prompt matches the suite) and `quote_fidelity` (segments of 12 or more characters in double, single, curly or guillemet quotes occur in the cited text; an apostrophe inside a word opens no quote). Any critical code turns the harness `choice` into `defer`; the model's own recommendation stays in `author_choice` (`forced_defer`). Without the gold the verifier cannot know which authority governs: a `charge` whose first issue is another eligible offence, with all of that offence's elements marked supported, passes the gate and is caught only by the grader.

**Grading** (`grading.grade`). The fourteen criteria, and errors classified apart from them: `fabricated_citation` and `unsupportive_citation` (a real, eligible authority that does not govern) are different codes, as are `wrong_version`, `pinpoint_mismatch`, `absent_element`, `false_charge` and `dangerous_commitment`. Without a grader entry a row is `pending`, never zero; a response without a valid output is a scored zero. A row passes (`quality_pass`, `all_pass`) only when every criterion holds, no reviewed dimension failed and no critical code stands, whether the verifier or the grader found it. The score detail keeps the two apart: `errors` holds what the grader found (the `error.<code>` rates count these only) and `verifier_codes` the verifier's critical codes; the private union of both decides the pass and the review, a nonexistent or ineligible cited version once (the verifier's `unknown_version` and `ineligible_version` are the grader's `wrong_version`). The public row's `critical_errors` counts the verifier's codes only (1 for a response without a structurally valid output): the grader's codes depend on the gold, and with the verifier codes visible in `reason_codes` their count would give the gold away. Adjudication is per code: dismissing `wrong_version` dismisses every `wrong_version` of that record. Semantic entailment, admissibility, defense arguments and sufficiency stay pending until a validated human or judge review supplies them, and a reviewed `fail` fails the row. `grading.aggregate` declares every denominator and the missing records (`missing.pending`, `missing.unavailable`, `missing.no_response`) and reports author and workflow decision risk separately; `bootstrap` and `paired_difference` resample matter families.

**Memo.** `render.render_memo` renders Markdown from fully validated JSON only, every untrusted string escaped exactly once with `ingest.escape`: banner, question, facts and limitations, elements and alternatives, defense and adverse evidence, authorities with their eligibility decision, missing evidence, proposed disposition, sourced claims (deterministic checks only) and an empty reviewer section. Memos stay in `local/memos/`.

**Score and review.** `score` takes `output_manifest` (`<attempt>/local/output-manifest.json`, written last by a generation or workflow run) and optionally `review_file` with `review_key`. It plans only when every listed file has its recorded size and digest and the manifest's identity matches its attempt: `attempt_id`, `job_id`, `mode`, suite, role digests, a legal `job.json`; the number of rows equals the manifest's `outputs` and the metadata's `rows`, and the rows are exactly the suite's matters times the job's arms times its repeats; the metadata's roles are the public view of the job's roles; manifest, job and metadata agree on `arms`, `template_sha256` and `data_class`; and `result.json` (written after the manifest, so it cannot be listed by digest) holds exactly the result the manifest records, `succeeded`, plus the worker's `finished_unix` and `attempt_id`. The planner, the coordinator and the worker check the same bytes. A limit remains: all these files are written by the operator of the attempt, so a fully consistent forgery cannot be told from a real attempt by these files alone; where the attempt sits in its campaign layout, the manifest digest must also equal the one the coordinator recorded in `campaign.json` when the attempt finished (see Lineage below). It grades the stored outputs, copies the verification, and writes a new attempt (`execution_kind: score-only`) with lineage keys and scorer and reviewer fingerprints; the source attempt is never written. `python -m llm_eval.experiments.legal_benchmark.grading packet --output-manifest FILE --output DIR` writes a blind review packet (every valid output with its critical codes; item ids drawn at random and an order drawn from a secret seed, so nothing in the packet names or lets one derive an arm, model or deployment) and a private key table (the item ids with their matter, arm and repetition, the order seed and the digests of the packet and of the output manifest), outside any attempt directory, any `reports` or `model_judgment` directory and the repository. Blind review depends on the key table staying private, and a reviewer may still guess an arm from the content of an output (a `no-context` output, for example, cannot cite shown passages). Review files are unsigned: an operator who can edit the review, the key and the packet digest together can write any review; the binding protects against mix-ups and reuse, not against the operator. `score` rebuilds the packet from the outputs it scores with the key's ids and order and refuses a review whose key names another output manifest or whose packet digest does not match; the reviewer fingerprint covers the reviewer, the rubric version and the packet digest. An adjudication with `upheld: true` means the error stands and the row fails; `upheld: false` dismisses it. A review file names its reviewer by a random 32-hex token from the operator's registry and holds closed verdicts and adjudications per item; a row is `reviewed` only when all four dimensions are reviewed and every critical code is adjudicated. No judge model is called by this package.

**Host requirement.** A job that is not a fixture states what it needs through `legal.host_requirements`: `score`, and runs whose roles are all CPU-served, pass worker preflight without the hardware-profile GPU, while every other preflight check (input hashes, code revision, clean checkout, OS, the WSL lock root) still applies. A job with a GPU-served role, and every job of the other experiments, keeps the GPU check. A role that is GPU-served but declares `accelerator: cpu` skips the check, and nothing verifies the claim; it is recorded in the role digest and the metadata.

**Rows.** `requests.jsonl` holds ids, enumerated statuses, reason codes, counts and timings only: no text, citation, path, gold label, `decision_correct` (with `choice` it would publish the gold recommendation) or digest of the prompt or the shown passages (`prompt_sha256` is kept in `local/attempts.jsonl`). Rows of the `reference` arm publish no number, digest, decision or reason code beyond the backend codes, and their `error_type` is only `error` or null; the real values stay in `local/`. `pending_dimensions` is empty on `error` and `missing` rows. Per-matter `choice` or `abstained` together with `quality_pass` or `criteria_passed` is still a gold label channel, so the projection publishes no per-matter row of these modes, only cohort aggregates. `ingest.escape` replaces zero-width joiners and non-joiners and the soft hyphen with U+FFFD, which is lossy for scripts and sequences that need joiners (Persian, Indic conjuncts, emoji sequences). Every value produced against the scripted test server is a fixture, not a measurement.

## Serving profiles, routing and exports

**Approved suites.** `approved-suites.json` lists, by the SHA-256 of their lock, the suites whose text or grader outcomes may leave the plugin (`contracts.approved_suites`, `contracts.export_allowed`). It holds the two shipped fixture suites, `original-smoke` and `original-packets`. A suite lock's own `data_class` authorises local execution and nothing else: a relocked copy of a shipped suite has another digest and is refused for every export, whatever its label says. Adding a suite to the list is a reviewed change.

**Locked serving profile.** `python -m llm_eval.experiments.legal_benchmark.profiles freeze --campaign-dir DIR --job-id ID --attempt-id ID [--measurement NAME] [--observed-placement gpu_layers=20,threads=8] --output FILE` reads exactly one named attempt of one `model-offloading` job and writes locked serving profile v1: source campaign, job and attempt with the digests of the files read, code revision, harness version, OS, driver, runtime build, artifact, template and tokenizer, requested and attested placement, memory reserve and peaks, paging, throughput medians and a probe outcome (`passed`, `failed`, `inconclusive` with reason codes). Every leaf states its nature (`observed`, `attested`, `declared`, `unavailable`); a missing value is `unavailable` and never estimated. Of the operator's free-form `hardware_attestation` only `os_build`, `nvidia_driver` and `paging` (`none` or `observed`) are read, each as one token; a placeholder (`REPLACE...`, `TODO`) counts as unavailable; free text, paths, endpoints, PIDs and host names are never copied. Paging is `observed` only from the sampled swap counters (at least two non-null samples of one counter) on an OS where they mean something; on `windows-11-native` the counters are always zero, so paging there is `unavailable` (probe `inconclusive`, `paging_unknown`) unless the operator attests it. The runner's own `memory_assessment` is not used. The probe fails on `job_not_succeeded`, `request_errors`, `paging_observed`, `placement_mismatch` (the attested placement differs from the requested one) and `memory_reserve_exceeded` (peak system memory above host RAM minus `host_reserve_gib`, or peak GPU memory above VRAM minus `gpu_reserve_gib`), and is inconclusive on `paging_unknown`, `placement_unobserved`, `all_responses_truncated` and `no_measured_requests`. The memory reserve is checked only when the attempt's host record has the RAM and VRAM totals (`memory.reserve_checked`); without them the reserves and peaks are informational. The outcome is a function of the profile's values: a profile whose stored outcome does not follow from them is refused when it is loaded. The offload result has no observed placement, so a profile without `--observed-placement` is `inconclusive` and cannot qualify a role. A synthetic job or measurement, an unknown attempt, an unnamed measurement among several, a campaign record and `result.json` that disagree on the attempt status, a `plan.json` that does not match its `plan_sha256`, and a declared OS that differs from the observed environment are refused; nothing picks "the newest" result, and the attempt directory is found by the scheduler's layout, never by a stored path. The profile records the physical host id and the hardware profile of the measured job. A role binds to its profile with `"qualification": {"serving_profile": "<path relative to the case>"}` (a path key: the planner pins the file); `validate_role` loads and binds it, and refuses a role whose platform, backend version, artifact, quantization, template, tokenizer revision, model revision (against the artifact's source revision) or placement differ (and, for chat roles, whose context differs or whose output budget exceeds the profile's), a profile in which one of those values is unavailable, a profile not measured on the legal-shaped export of an approved suite (`profiles.approved_workloads()`, default arm and settings), and a profile that did not pass. Embedder, reranker and selector roles bind on the same identity fields except the chat template and tokenizer revision, which bind chat roles only. Qualification runs the legal-shaped chat workload, so it measures chat serving: an embedder or reranker qualified this way is bound by host, runtime, artifact and workload only, not by any measurement of embedding or rerank requests. Public metadata reports `qualified_by_attestation: true` when the bound profile's paging or placement is an operator attestation (placement always is, today), so an attested qualification is never presented as measured. A WSL guest cannot see the host paging its VM, so WSL needs the paging attestation like Windows, and a profile claiming observed paging on either is refused. Placeholders are values beginning with `REPLACE_WITH_` or `TODO` (case-sensitive). At run time `check_job` requires the profile bytes to be the planned ones and the profile's physical host to be the host that serves the role; for a role on the job's own host also the job's hardware profile and OS. A separately hosted service's OS and hardware profile are not part of the job, so they are not compared. What the pinned digest proves: only that the profile's bytes did not change after planning. The profile's source attempt is not re-read at bind time, and the driver is recorded but not compared at run time. A bound role is `qualified: true` in the metadata with `serving_profile_sha256`, and the profile digest is part of the role digest. `profiles workload --suite LOCK --output FILE` writes the legal-shaped task suite for `model-offloading` (every matter's full `lexical-eligible` draft prompt); the shipped `workloads/qualification/legal-shaped.json` is that export of `original-smoke`. The commands refuse an output inside an attempt directory, under a directory named `reports` or `model_judgment` in any letter case, or inside any repository (an ancestor directory holds a `.git` entry, which also covers a worktree nested in another checkout) (`contracts.check_output`, the rule `grading packet` uses), so a changed shipped workload is written elsewhere and copied in as a reviewed change.

**Role hosts.** Every externally served role's host (`resource_host`, else the job's own host) must be reserved by the job (`Role host is not reserved by this job: <role>`). A separately hosted service is reserved by listing its physical host under `resource_hosts` of the job's target and by an inventory target whose `physical_host_id` is that host. `legal.setup_platforms` answers from the roles (only `serving: managed`, which is gated), so a legal campaign installs nothing; `readiness.select` asks `host_requirements`, so a campaign whose roles are all CPU-served needs no GPU and stays a `model-run`.

**Selector.** `generation` and `workflow` take an optional `selector` (`router`, `policy`, `calibration`). A `fixed` or `category` router runs in-process; a `systemone` router is the local role `roles.selector` (`capability: decision`, `protocol: json`), on the job's endpoint allowlist, and its `criteria` must contain `insufficient_evidence` and `insufficient_authority`. Labels are identifiers and never a path key. `policy.fallback` (an arm of the case) is the safe deterministic fallback. The selector sees one route-time message per matter (question, operative date, venue, evidence source counts per kind) and chooses among the case's arms with one fixed generator; arms that `retrieval.available_arms` cannot run are not eligible, and the `reference` arm cannot be routed. An insufficiency label defers without a generation request; a router error, a missing confidence (with `require_confidence` or a threshold), a probability below the threshold, a removed candidate and an ineligible choice take the fallback, and when the fallback is not eligible the matter defers (`no_eligible_candidate`). Rows of a routed job have `arm: routed`, `category: routed` or `routed-defer`, and the route keys `routed`, `route_choice`, `route_selected`, `route_fallback`, `route_confidence`, `router_s`. A deferral is a scored row with nothing passed (`forced_defer: true`, `abstained: false`), so deferring cannot remove matters from the denominator; its correctness stays in the private score detail (`selector_deferral`). Every decision goes to `local/route-decisions.jsonl` as hashes, choices, numbers and codes, never the messages. A threshold above 0 needs a served selector and a pinned `calibration`: `{"calibration_file": <record>, "suite": <calibration suite lock>, "routed": {"output_manifest": <manifest of the routed calibration attempt>}, "fallback": {"output_manifest": <manifest of the fallback attempt>}}`. The suite's pinned files and every file both output manifests list (with their `result.json`) join the job's inputs. At plan time the two manifests are verified as `score` verifies them, `calibration_rows` and `calibrate` are run again over their pinned outputs at the record's thresholds, and the record must equal the result exactly, so a hand-written record is refused. The routed calibration attempt must have run with no threshold and `require_confidence: false` (with a threshold, a below-threshold row already took the fallback and its routed quality is no counterfactual); the record must name that suite, carry the policy's threshold and pass `routing.check_threshold`: another lock and split, no family of the evaluation suite, and no shared family, amendment pair or near duplicate in the split audit. With the shipped data a threshold is calibrated on `original-packets` and used on `original-smoke`. Both splits are small; nothing calibrated on them supports adopting a selector.

**Routing export and replay** (`python -m llm_eval.experiments.legal_benchmark.routing`). `export` writes the routing suite (`benchmark: legal-routing`, route-time messages only, no label or outcome) of an approved suite. `replay` builds the replay manifest of the routing experiment (`suite_sha256`, `candidate_fingerprints`, one row per task and recipe with `quality` = mean `criteria_passed / criteria_total`, a scored invalid output as 0.0, unscored rows absent) from attempts of that suite, and a local sidecar `<manifest>.provenance.json` with the suite lock, rubric version, scorer fingerprint, the fixed generator (`generator_sha256` and its identity), originating attempts (with the `reviewer_fingerprint` of the review a score attempt used, null without one), per-matter outcomes and, with `--calibration`, the digest of the calibration record a selector threshold came from. Quality and outcomes are computed by grading the outputs each attempt's output manifest pins, as the `score` mode does, after the manifest's identity, file digests and rows are checked; an attempt's own `score-detail.jsonl` is never read. Every attempt must have the same generator role, and every `--candidates` entry must be exactly that generator's identity (`model`, `model_revision`, `platform`, `backend_version`, `protocol`, `quantization`, `template_sha256`, `context_tokens`). `verify --attempt DIR ...` checks what the routing experiment does not (orphan rows, values out of range, stale scores, outcomes that do not match the rows, candidates that are not the fixed generator, originating attempts) and rebuilds the manifest and the sidecar from the named attempts; it must run before any `llm-routing` replay. `evaluate` compares fixed candidates, category rules, a seeded latency-matched random baseline and recorded selector decisions on the same tasks, with fallbacks, abstentions (a deferral counts as a covered task with quality 0, safe and not passing, and with no latency, so a strategy cannot raise its means by deferring hard tasks), switches, reprefill tokens, unsafe commitments, false-charge and all-pass rates, risk versus coverage, the means over the tasks every strategy covers (`common_*`) and, with `--calibration`, whether a selector was evaluated on families it was calibrated on (`calibration_overlap`); strategy names are unique, and no strategy may select `reference`; for a suite that is not approved it works from the attempts in memory and writes nothing. `calibrate` writes a calibration record from a routed and a fallback attempt on the calibration suite (the fallback attempt runs the routed policy's fallback arm); the record carries the selector identity (`routing.selector_identity`: router rule, policy without the threshold settings, served role), both output manifest digests and the generator digest, and a job may use it only with that selector and generator, on an approved calibration suite whose split, families and matter count it matches, at one of the thresholds it calibrated. A matter the routed run deferred counts its deferral at every threshold, as `route` would. A routing or offload bundle built from these exports carries `legal-routing` or `legal-shaped`, which this plugin claims, so it cannot be published. That refusal depends on the benchmark name, so `publish_report` also refuses such bundles by content: a bundle whose pinned inputs or rows match a legal export is refused whatever its name (see Publication below).

**Formats the projection reads.** Routed rows carry the route keys `routed`, `route_choice`, `route_selected`, `route_fallback`, `route_confidence` (six decimals), `router_s` and `route_error_type` (the class name of a router exception after which the fallback ran; `error_type` stays the generation's own and is null on an `ok` row). A selector deferral's score-detail record has the key `selector_deferral` (an insufficiency label or `no_eligible_candidate`), and its `local/retrieval-results.jsonl` entry has `result: null`. Replay manifests, their sidecars and calibration records hold per-matter values derived from the gold (quality, decision outcomes, risk per threshold): they are local operator files and are never public, also when the suite is a public fixture. Every value these commands produce against the scripted test servers is a fixture, not a measurement.

## What stays local

Candidate drafts and grader detail (`local/candidate-outputs.jsonl`, `local/score-detail.jsonl`, and for the generation modes `raw-responses.jsonl`, `attempts.jsonl`, `verification.jsonl`, `retrieval-results.jsonl`, `memos/` and `output-manifest.json`) are written to `local/` inside the attempt directory. The generic report builder scans the attempt directory by file name at any depth, so `local/` is private by naming rule, not by directory: every private file is created through `contracts.private_file`, which refuses a name that builder exports, and `execute` refuses an attempt directory below a directory named `model_judgment` or `reports`. A legal report never goes through that scan: it is built by the projection below, which reads `requests.jsonl` and `metadata.json` at the attempt root and, to aggregate, `local/score-detail.jsonl`, and nothing else.

`execute` loads the suite once and requires the digest of the lock bytes it parsed to equal the digest the planner recorded for the case's `suite`; the lock pins the manifests. A suite changed after planning fails before anything is written, even when it was relocked consistently.

## Classification, gates and the report projection

**One classification.** `reporting.classify(job)` decides what a legal job may do, from the planned job, the files it pins and the reviewed list `approved-suites.json`, and from nothing else: no report label, manifest field, campaign setting, case field or caller argument. It never raises. A job is `approved` when its suite lock is verified (the lock digest on disk equals the digest the planner recorded, and every pinned file verifies) and the lock digest is in the approved list with the same `benchmark_id`; `declared` when it is verified and its own lock says `public-synthetic` (or `public-benchmark` with every dataset gate verified) but it is not approved; `refused` for `private-matter`, a blocked dataset gate, or anything that does not verify (`unknown_mode`, `lock_missing`, `planned_digest_mismatch`, `lock_invalid`). The label a lock author writes is never more than `declared`. `approved` allows local and SSH runs, collection and a local report, and, with an authorization, manual publication; `declared` allows a local run and a local, reduced report, and nothing leaves the host; `refused` allows nothing.

**The gates.** The same classification is checked at plan time (`Job is not admitted by the data policy`, and `Remote execution is not available` for an `ssh` target that is not approved), by the scheduler before an attempt is journaled (the job fails with reason `data_policy`; no attempt, directory, reservation or RPC), by the worker before it reserves or starts a child (`Data policy refused the job`, after the input-hash and revision checks), on both sides of a remote collection (the coordinator records `collect: refused`; the worker refuses `collect` and `file-chunk` for any directory at, inside or above a non-transferable attempt: `Collection refused by data policy: <job.json path>`; every `job.json` at or above the path decides, so a nearer one cannot override a refusing one above it, and a `job.json` that cannot be read as an object naming its experiment refuses), at finalization (receipt `disabled` with the reason code, or `failed` with `ProjectionRejected`; the attempt files are never touched) and at publication. `include_outputs` and every other reporting setting change nothing for a legal job. Automatic publication stays refused: `publish.mode: pull-request` fails at plan time and finalization never publishes; the shipped examples use `"mode": "none"`.

**Plan drift.** `run_campaign` refuses a stored `plan.json` whose content does not match its `plan_sha256` (`Campaign plan changed; create a new campaign`); the legal projection and `verify_publication` refuse it too (`plan_changed`), and also refuse a plan without the key when it holds a legal job (the planner has always written it). This detects drift of the stored plan (an edit that forgot the digest), not forgery: a forger recomputes the digest, which is why the classification trusts nothing in the plan that it cannot re-derive from files on disk and from the approved list, why an exact export requires the attempt metadata to name the lock's benchmark, revision, split, jurisdiction, rubric and policy, and why the attempt receipt names the suite lock. Hand-built plans of the other experiments without the key run and report as before.

**The projection.** A legal report is the projection, never the generic scan: a strict recursive allowlist of enumerated categories, opaque ids, hashes, versioned numbers, approved settings, coverage and coarse status. An unexpected key, a wrong type, free text or a path anywhere is `ProjectionRejected` with a schema position (`request.category`, `request.<unknown key>`), never a value. A symbolic link anywhere from the campaign directory down to a file read, and a campaign directory under a directory named `reports` or `model_judgment`, are refused. The bundle holds exactly `README.md`, `manifest.json`, `summary.json`, `summary.csv`, `resolved-config.json`, `legal-summary.json` and `raw/measurements.jsonl.gz`, no chart, all written as canonical bytes (sorted JSON with LF, CSV with LF, GZIP with a fixed header and stored blocks) before they are hashed. Per-matter rows leave for the `smoke` mode only: exactly, for an approved suite with `fixture_export` (its matter ids and `expected_choice` are fixture data), and reduced otherwise (ids replaced by salted pseudonyms from `projection-salt` beside `experiment.json`, which never enters a bundle; scenarios become `all`; decision, quality, hash and token keys dropped; the strings of the lock omitted). The `retrieval`, `generation`, `workflow` and `score` modes publish no per-matter row at all: per-matter `choice` or `abstained` with `quality_pass`, and the per-matter retrieval metrics, are gold label channels. `legal-summary.json` carries one cohort per job and arm with every metric as `{value, n, low, high, missing}`: counts by row status, the means of the eleven retrieval metrics, medians and 95th percentiles of the timings, the truncation, revision, fallback and selector-deferral rates, and every `grading.aggregate` metric over the validated score detail (family bootstrap intervals for the pass, criterion and error rates; both class confusions; `critical_errors` and `critical_unreviewed`; the three kinds of missing score), plus paired differences between the arms of a generation, workflow or score job. The legal summary grades every arm, the reference arm included; `summary.json` excludes the reference arm (its rows publish no number), its `quality_pass_rate` is the exact-version pass rate for a retrieval job, and it has no quality rate under a reduced projection. A cohort covers experiment, mode, execution kind, data class, suite and split, policy, rubric, scorer and reviewer, arm with the retrieval settings and selector, every role digest, the generator's model, revision, artifact, quantization, platform, backend and protocol, the prompt template, the generation settings, OS, hardware profile, accelerator, context and output budget; two runs are comparable only when their cohort digests are equal.

**Publication.** The plan of issue 45 states: "No authorization to access private matter inputs or publish a results bundle is implied by this plan." `llm-eval publish-results` publishes a legal report only when `reporting.verify_publication` passes, in this order: the report sits in its campaign layout under a campaign directory named as `scheduler.initialize` names it (`provenance_missing`); the manifest carries the projection marker and canonical bytes (`legacy_report`); the stored plan matches its digest (`plan_changed`); every job of the run is `approved` by the installed package's own approved list (`unverified`, `not_approved`; the `--project-root` of the command names the repository for Git only, so a crafted directory approves nothing), and by the approved list as committed on the remote base branch, fetched with an explicit refspec into the private ref `refs/llm-eval/publish-base` (`not_approved_upstream`: a local edit of the list, a local commit or a moved `origin/<base>` approves nothing; the private ref is deleted when the publication ends, published or refused); the latest attempt of each job succeeded, its metadata names the approved lock, and the coordinator's receipt in `campaign.json` holds the digests of `requests.jsonl`, `metadata.json` (and so of the lock it names), `local/score-detail.jsonl` and the output manifest as they are now; a `score` job also needs its source attempt to sit in a campaign layout whose record holds the digest of the output manifest it scored (`receipt_mismatch`); the bundle and `publication.json` equal, byte for byte, the projection rebuilt from those inputs (`bundle_mismatch`: an edited file, label, repository, base branch, draft flag or recomputed fingerprint); and `publication-authorization.json` in the campaign directory names this run, fingerprint, suite locks, repository and base branch (`not_authorized`). A report manifest's own labels authorize nothing. `python -m llm_eval.experiments.legal_benchmark.reporting authorize --campaign-dir DIR --experiment-run ID --approved-by ROLE` verifies the report, shows what would be published and writes the authorization only after the run id is typed back on an interactive terminal; it is the separately authorized step, and nothing in this repository runs it. During publication every staged and committed file under the report path is compared with the manifest that was validated before push (`Staged files differ from the manifest`, `Committed bytes differ from the manifest: <file>`), a publication branch whose content differs from the fetched base in `approved-suites.json` is refused (`Publication branch changes a protected file`), and nothing is re-hashed or re-receipted to make bytes match; `*.gz` is `-text` in `.gitattributes`. Historical bundles of the other experiments are not touched and are not blob-checked.

**Lineage.** When an attempt finishes, the coordinator records in `campaign.json`: `file_sha256` (the digests of `requests.jsonl`, `metadata.json` and `local/score-detail.jsonl` where present; the digest of `metadata.json` binds the suite lock it names) and, for a generation or workflow attempt, `output_manifest_sha256`. The projection refuses an attempt whose files differ from a receipt that names them (`receipt_mismatch`); publication also refuses a receipt that is missing. `score`, the routing replay verification and calibration read a source attempt only through `grading._manifest`, which, when the attempt sits in its campaign layout, requires its record to hold the manifest's digest (`Output manifest differs from the campaign record`, or `Campaign record has no output-manifest digest (campaign written before this check)`). An attempt copied out of its campaign layout has no record to check against: it can be scored locally, and a score job over it cannot be published. An attempt in a campaign written before this package therefore cannot be scored, replayed or used for calibration in place (copy it out, or re-run it); a smoke campaign of that age still resumes and gets its local report, and cannot be published. An unreserved role `resource_host` is refused at run start, not at plan time.

**Small cohorts.** In a projection that is not an exact fixture export (any suite without `fixture_export`), a cohort of fewer than five distinct matters (`MIN_COHORT`; the matters of its rows and score details) publishes no number: it is marked `suppressed: true` with `run_status: null`, every metric name the mode can produce is present as `{value: null, n: null, low: null, high: null, missing: null}`, its paired differences are all null, its job has no row in the generic `summary.json`, and the bundle README says only that the cohort is too small. Presence, absence and counts therefore carry nothing about the matters' labels or outcomes: two such runs over different matters publish equal metrics. In a cohort of five or more matters, every number computed over fewer than five matters, and every confusion cell whose gold class has fewer than five matters, becomes `{value: null, n: 0, low: null, high: null, missing, suppressed: <withheld count>}`; paired differences over fewer than five common matters follow the same rule, and the metadata `all_pass` count is null. The generic `summary.json` of such a projection carries no quality, decision or abstention value at all, only counts and timings. Differencing is not prevented: two reduced runs over overlapping subsets (five matters and the same five plus a sixth) can be subtracted to give the sixth matter's result. Exact fixture exports are exempt: their answer key is public by design.

**Other experiments' bundles.** `publish_report` refuses a bundle of any experiment that carries legal content: a manifest with the projection keys (`projection`, `canonical_bytes`, `execution_kinds`, `data_class`, `suite_lock_sha256`, `cohorts`), a file named `legal-summary.json`, rows or metadata with `suite_lock_sha256`, `family_id`, `review_status` or a route key of this plugin, a benchmark name that after NFKC normalisation, case folding and removal of `-`, `_` and spaces equals one this plugin writes (`legal-smoke`, `legal-routing`, `legal-shaped` or the benchmark id of an approved suite), any row whose normalised task id is a matter id of an approved suite, an approved suite file among its input hashes or pinned inputs, an export task list of an approved suite (whole, or any single task's messages, in any order or count), a replay manifest over an approved routing export or over approved matter ids, the text markers of the exports, and any text file of the bundle (`README.md`, `summary.csv`, the JSON files, the decompressed raw archive) that after NFKC normalisation and case folding contains `legal-benchmark` (also part of every legal run id), `legal-smoke`, `legal-routing`, `legal-shaped`, the benchmark id of an approved suite or a legal cohort metric name. The refusal names the class of the mark (`Publication identity mismatch: the bundle carries content of legal-benchmark (text file)`; the classes are `manifest key`, `legal summary`, `input file`, `row key`, `benchmark name`, `task id`, `export task`, `text marker`, `text file` and `pinned input`), never bundle text; a benchmark name this plugin writes is refused earlier with its own message (`the bundle carries a legal benchmark name`). A public legal benchmark is not such a name: a bundle of `model-offloading` or `llm-routing` that measures `LegalBench`, or has rows in category `legal`, publishes unless it carries one of the marks above. When the report sits anywhere below a campaign directory (the nearest directory above it with a `plan.json`, whatever the directories in between are called), the campaign record must not name another experiment (`Publication identity mismatch: the campaign record names legal-benchmark`): in the standard layout the plan's experiment and jobs of its run, its experiment record and each attempt's `job.json` and `metadata.json`; elsewhere below the campaign, those of every run. A campaign layout is not required for every publication: the published bundles of the other experiments are dry-run from bare copies, and requiring a layout would change that result for all twenty of them.

**Threat model and what remains.** The gates stop mistakes, lazy relabels and partial edits by an operator, and let no unapproved or private suite's numbers out through this code without a deliberate forgery of several files. They do not stop a person who rewrites every file by hand. A hand relabel that passes must: rename every experiment label (publication spec, manifest, resolved configuration, jobs, report and chart paths); remove `legal-summary.json`, the projection keys of the manifest and the row keys `family_id`, `review_status`, `suite_lock_sha256` and the route keys; rename every benchmark name this plugin writes (`legal-smoke`, `legal-routing`, `legal-shaped`, the benchmark id of an approved suite) and every task id; rewrite `README.md` and every other text file, the raw archive included, so that no legal marker above remains, including the legal run id in the report directory name and the publication id; and move the report out from below any campaign directory, or else relabel the plan, the experiment record and every attempt's `job.json` and `metadata.json` too. Such a bundle carries no mark this code can recognise, and a person can push any bytes with their own Git client. A consistent forgery of `campaign.json` together with the attempt files and the output manifest also passes the receipt checks. Review of the publication pull request is the remaining control.

**Not built here.** No legal bundle is published by this repository. Private matter is never transferred or published in any form; the class exists so that every gate can refuse it. Authentication of `plan.json` with a key is not built.

## Changing the fixtures

Edit the three manifests, regenerate span and text digests, write the dict that `contracts.make_lock` returns as the new lock (LF line endings), and replace the suite's entry in `approved-suites.json` with the new lock digest as a reviewed change. Until then the edited suite is `declared`: it runs and gets a local, reduced report, and nothing leaves the host.
